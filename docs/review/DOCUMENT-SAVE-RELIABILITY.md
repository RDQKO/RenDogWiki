# 문서 저장 실패 점검 및 안정화

2026-11-23, 사용자 첨부 콘솔의 `/api/save` 504와 코드·DB 통계·격리 재현을 기준으로 점검했다.

## 확인한 사실과 진단의 한계

첨부 오류는 HTTP 504다. 400 오류는 별도의 자원 요청이므로 같은 저장 원인으로 단정하지 않았다. 저장 API의 기존 최대 실행 시간은 30초이고 DB는 공용 연결 하나를 사용했다. 인증·메타데이터 조회도 저장 트랜잭션 앞에서 이 연결을 기다렸다. 트랜잭션 안의 `statement_timeout`과 `lock_timeout`은 연결 대기 시간을 제한하지 않는다.

DB의 최근 통계에서 문서 UPDATE 최대 실행 시간은 약 37ms, 본문 UPSERT는 약 18ms, 해당 검색 인덱스 INSERT는 약 154ms였다. DB 로그에서 같은 시각의 statement timeout이나 deadlock은 발견하지 못했다. Vercel 런타임 로그는 해당 팀 권한 403으로 조회하지 못했으므로, 첨부 요청이 정확히 어느 단계에서 30초를 소비했는지는 확정할 수 없다. 빠른 쿼리 통계만으로 연결·네트워크·실행 환경 지연이 없었다고 단정할 수도 없다.

코드에서 다음 두 취약점을 확인해 보완했다.

1. 공용 단일 연결의 선행 읽기 작업 때문에 저장이 대기할 수 있었다. 격리 Postgres에서 공용 연결을 예약해 둔 상태에서도 새 저장 연결이 완료되는 것을 재현했다.
2. DB COMMIT 뒤 응답이 유실되면 성공 여부를 확인할 방법이 없었다. 같은 신규 저장을 다시 보내면 중복 제목 충돌, 같은 기존 문서를 다시 보내면 수정 시각 충돌로 실패할 수 있었다. 실제 COMMIT 뒤 연결 오류를 발생시켜 재현했다.

## 수정

- 저장 요청은 별도 최대 1개 연결로 인증·스키마 조회·트랜잭션을 수행한 뒤 연결을 종료한다. 일반 읽기용 공용 연결의 대기열에 들어가지 않는다. 저장 중에만 추가 연결을 사용하므로 TLS 연결 비용은 발생한다.
- 저장 API 실행 여유를 60초로 늘리고 DB와 같은 서울 리전을 명시했다. 트랜잭션은 잠금 대기 3초·문장 실행 8초로 제한한다. 실제 제한은 배포 플랜의 상한을 따른다.
- 새 에디터는 저장마다 UUID를 보낸다. 서버는 사용자·본문 및 메타데이터의 해시·결과를 문서와 같은 트랜잭션에 기록한다. 같은 요청은 기존 성공 결과를 반환하며 문서·검색 인덱스·활동 로그를 다시 쓰지 않는다.
- 같은 UUID를 다른 사용자나 다른 내용으로 재사용하면 409를 반환한다. 같은 문서의 다른 사용자가 먼저 저장한 경우 기존 수정 시각 검사를 유지한다.
- 네트워크 오류나 500/502/503/504 응답은 같은 UUID와 같은 내용으로 한 번만 자동 재시도한다. 성공 여부가 불명확하면 해당 탭에서 이전 요청을 먼저 확인한다. 그동안 수정한 내용은 보존하고 이전 저장 확인 후 다시 저장하도록 안내한다.
- DB가 롤백을 확인한 지연 오류는 `outcome: not-saved`로 구분한다. 장기 연결 오류를 무조건 새 저장으로 반복하지 않는다.
- 본문·메타데이터·검색 인덱스는 계속 한 트랜잭션으로 반영한다. 보조 로그는 응답 이후에 기록한다. 추적 ID·단계·소요 시간을 로그에 남기고 `X-Save-Trace`를 응답에 넣는다. 본문이나 인증 비밀은 로그에 넣지 않는다.

## 검증

- 실제 격리 PostgreSQL: 응답 유실 후 신규 문서 중복 생성 방지, 동일 요청 재전송의 동일 결과와 수정 시각 보존, 요청 ID 변조·다른 사용자 재사용 거부, 공용 연결 점유 중 저장 완료.
- 기존 저장 검증 유지: 잘못된 본문 거부, 검색 인덱스 실패 시 전체 롤백, stale editor 409, deadlock/lock timeout/serialization failure의 확정 롤백만 재시도, 캐시 실패와 보조 로그 지연의 성공 응답 보존.
- 클라이언트: 504 HTML 응답과 네트워크 실패 후 같은 UUID·본문 재시도, 충돌 응답을 추가 쓰기 없이 반환.
- 실제 로컬 Next HTTP: 로그인 후 저장, 같은 UUID 재요청의 성공 결과 재사용, 다른 UUID의 낡은 수정 시각 충돌, 검색 및 본문 재조회.

`document_save_requests`는 본문 복사본이 아니라 작은 해시와 결과만 보관한다. RLS와 직접 접근 차단을 적용했고 관리자·작성자 확인을 거친 서버 저장 경로에서만 사용한다. 기존 문서·이미지 내용은 마이그레이션으로 변경하지 않았다.
